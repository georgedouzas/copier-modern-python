# Implementation Plan: Project Layouts

**Branch**: `001-project-layouts` | **Date**: 2026-07-24 | **Spec**: [spec.md](./spec.md)

**Input**: Feature specification from `/specs/001-project-layouts/spec.md`

## Summary

Add a `project_layout` question to `copier.yml` offering `library` (default), `script`
and `ml`, and make the generated source tree, dependency set, documentation shape and
applicable nox sessions follow from it. The library answer must render byte-identical
output to today, which is enforced by the existing golden fixtures rather than by review.

The approach is **conditional rendering inside the existing template**, not a per-layout
template tree. `project/` already carries one spine — one `noxfile.py.jinja`, one
`pyproject.toml.jinja`, one docs tree — that branches on `git_provider` and
`package_manager`. Layout becomes a third branching answer using the same two mechanisms
already in use: Jinja conditionals inside files, and conditional path names such as
`{% if git_provider == 'GitHub' %}.github{% endif %}`. This keeps the quality floor
literally shared rather than copied, which is what makes FR-006 and FR-007 hold by
construction instead of by vigilance.

## Technical Context

**Language/Version**: Jinja2 templates rendered by Copier `>=9`; generated projects target
Python `>=3.11, <3.14`

**Primary Dependencies**: Copier (rendering), nox (generated task interface), bats (fixture
and integration harness), PDM and uv (generated package managers). Added to generated
projects by layout: `click` for script/CLI, `metaflow` plus notebook tooling for ML — each
exercised by a task, per FR-017.

**Storage**: N/A — the artifact is a rendered file tree

**Testing**: `make tests` (bats golden-fixture diff against `tests/expected/`), `make
tests-integration` (generate a project, then run its real toolchain)

**Target Platform**: Developer workstations and CI runners on Linux, macOS and Windows

**Project Type**: Copier template — the deliverable is generated projects, not a library

**Performance Goals**: `make tests` stays fast enough to run before every commit. The ML
layout pulls heavier dependencies, so integration runtime grows; that cost is accepted for
the integration suite only, which already runs on a schedule rather than per push.

**Constraints**:

- The library layout's rendered output must not change by a single byte (FR-002, SC-002)
- Layout must not multiply the fixture suite by the full cross product (spec Assumptions,
  constitution Principle III)
- No generated project may require manual repair after generation (FR-004)

**Scale/Scope**: 3 layouts × 4 git providers × 2 package managers. Fixture coverage is
representative, not exhaustive: currently 8 fixtures, growing to roughly 11.

| VI. Current Tooling, Deliberately Chosen | New tools earn their place, are integrated not merely installed | **GATE ACTIVE** — the ML layout introduces dependencies. **Result**: no unjustified violations. Complexity Tracking is empty.

The one live risk is Principle VI: an ML layout is an invitation to bundle a fashionable
stack. Phase 0 constrains the dependency set to what a session actually runs.

Principle VI moved from GATE ACTIVE to closed, though not the way the first draft expected.
That draft satisfied the principle by subtraction — no ML dependency at all — and in doing so
shipped a `notebooks/` directory with nothing able to open a notebook, which contract C5
forbids. R4a distinguishes a *modelling* library, which the practitioner owns and no template
task can exercise, from a *workflow* library, which is the scaffolding the layout was defined
to provide and which runs locally with no infrastructure. Metaflow clears FR-017 because
`python flow.py run` is executable by the generated tests; scikit-learn never could.

### Source Code (repository root)

```text
copier.yml                          # + project_layout question; publish_pypi gains a `when`

project/                            # the single shared spine, branching on answers
├── noxfile.py.jinja                # sessions gated by layout; docs session varies
├── pyproject.toml.jinja            # dependency groups and build config vary by layout
├── properdocs.yml.jinja            # nav and watch paths vary by layout
├── README.md.jinja
├── docs/
│   ├── generate_api.py.jinja       # library only — API reference needs an importable package
│   ├── index.md
│   ├── overview/
│   └── examples/
├── src/{{python_package_import_name}}/   # library and script layouts
│   ├── __init__.py.jinja
│   ├── py.typed
│   └── {% if project_layout == 'script' %}cli.py{% endif %}.jinja
├── {% if project_layout == 'ml' %}notebooks{% endif %}/   # ml only, with notebook tooling
├── {% if project_layout == 'ml' %}data{% endif %}/        # ml only, contents ignored (FR-019)
├── tests/
└── {% if git_provider == ... %}      # unchanged provider-conditional paths

tests/
├── test_copier.bats                # + one case per new layout
├── test_integration.bats           # + generate-and-run per layout
└── expected/
    ├── default/                    # library — must not change
    ├── script-layout/              # new fixture
    ├── ml-layout/                  # new fixture
    └── ...                         # existing provider and package-manager fixtures
```

**Structure Decision**: One shared template spine with layout-conditional rendering, using
the two mechanisms already proven in this repository — in-file Jinja conditionals and
conditional path-name directories. Rejected alternatives are recorded in `research.md`; the
decisive argument is that a per-layout template tree would fork `noxfile.py.jinja` three
ways, and the quality floor would then be three copies that drift, which Principle II exists
to prevent.
